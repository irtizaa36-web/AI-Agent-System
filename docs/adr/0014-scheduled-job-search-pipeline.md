# A scheduled job-search pipeline that is code first and a model last

ADR 0012 built `job-search-agent`: one draft-only agent that can read a job board and tailor a resume when a human invokes it, and it closed by naming the gap it did not fill — truly unattended daily delivery. This ADR fills that gap with a different shape of thing entirely. Not an agent: a deterministic pipeline, in `src/jobsearch/`, that a `launchd` job runs twice a day and that calls a model exactly once, in one stage, in batches.

**The agent was the wrong tool for discovery, and that is the central decision here.** An agent loop is the most expensive instrument this project owns — every posting becomes context, every judgement becomes a turn, and the cost scales with the market rather than with the candidate. Fetching a JSON endpoint, stripping boilerplate, hashing content, collapsing a role cross-posted to four boards, comparing a salary to a floor, and ranking by score are all deterministic; none of them need language. So all of them are scripts, and the model is handed only the question no script can answer: does this real posting fit this real person. That question arrives in batches of fifteen, behind a cached prefix, against postings already trimmed to a token budget. A steady-state run costs a few cents and the first backfill about fifty. The rule, stated so it survives the next feature: **a model is allowed where judgment or language generation is genuinely required, and nowhere else.**

**Never processing a posting twice is what makes the schedule affordable.** Every posting is content-hashed on arrival, and anything already seen is dropped before the filters, let alone the model. That single property is what lets the run be idempotent — a missed firing, a repeated firing, or a manual `npm run pipeline` in the middle of the day all cost nothing beyond the fetch — and idempotence is what makes an unattended schedule safe rather than merely convenient.

**The pipeline degrades instead of dying, because the failure it must never have is the silent one.** A source that 404s is marked degraded and named in the digest; a scoring batch the model fails on leaves its postings in `seen` so the next run picks them up; an unreadable record does not blind the store to every other record. The thing that would actually hurt is a pipeline that quietly stops finding jobs and does not mention it, so every failure surfaces in the digest she reads anyway.

**Two false-positive defenses are load-bearing and were both found by running against real boards, not fixtures.** A stated location now beats prose in the description: Figma's board advertises its own product as letting people "work together from anywhere in the world", which promoted an onsite Tel Aviv role into a remote-only search until the employer's structured `location` field was given precedence over marketing copy. And a posting that publishes no salary is never rejected by the compensation floor and never assumed to clear it — it passes, flagged `unknown`, and the scorer is told it is unknown. Rejecting silent postings would discard most of the market; assuming they qualify would be a guess. The same discipline that forbids inventing a resume bullet forbids inventing a salary.

**A new small port rather than a widened old one.** Scoring needs token usage (to report what a run cost) and prompt caching (to make batching pay off); the orchestrator's `ModelProvider` exposes neither, by design, because an agent Run needs neither. Widening that interface for one caller would have pushed a scheduled pipeline's concerns into the engine every Pack depends on, so `ScoringClient` is its own port in `src/jobsearch/`, with its own fake, following the same ports-and-adapters shape (ADR 0001) and the same built-ins-only rule (ADR 0002 — `fetch`, `node:test`, no new dependency).

**Delivery is a local file and a local page, which resolves ADR 0012's open question without weakening anything.** That ADR observed that a scheduled run cannot email a digest, because `send-email` is unconditionally approval-gated (ADR 0004) and a cron job has no human present to approve — and it declined to carve an exception. It does not need one. The digest is written to `.orchestrator/jobs/digests/` and served by a small read-only server (`orchestrator jobs dashboard`), so nothing outbound happens at all and the gate stays exactly as strict as it was. That server is deliberately separate from the coworker dashboard rather than a section inside it: that page is built around agent rosters and task kanban, a different domain with a different snapshot shape, and job search has no business reshaping it (ADR 0003).

**LinkedIn and Indeed keep the treatment ADR 0013 gave them.** Aggregator coverage comes from forwarded job-alert emails, not automation against a logged-in account — and the candidate here is employed and searching discreetly, which makes automated activity on her own account precisely the wrong risk to take. Phase 1's sources are public ATS JSON endpoints (Greenhouse, Lever, Ashby) and published feeds, each fetched with a real user agent, a concurrency cap and jitter: an operator who wants to rate-limit or block this pipeline can see it and do so.

**What this ADR does not do.** It does not tailor a resume, write a cover letter, prefill a form, or draft outreach — those are Phases 2 and 3, they involve a large model or a browser, and neither belongs in an unattended path. It does not enrich companies or look up salary data. And it does not move a single posting toward being applied to: `ApplicationRecord.status` has a `submitted_by_human` value that no code path in this repository sets, which is the point.

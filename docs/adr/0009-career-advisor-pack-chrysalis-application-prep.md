# Career Advisor Pack: the first real code for a planned Pack, built for a real application

PROJECT-BRAIN.md's Section 5 has always named "Medical Career Advisor" as one of four planned Packs, with no code written for it. A concrete real need arrived — helping a resident prepare an application to AAAAI's Chrysalis Project — and per this project's own build philosophy (Section 6/8: build when a real use case justifies it, not ahead of one), that's exactly the trigger to write the first real version, not a design exercise.

**Smallest fit: one new Pack, zero new Core concepts, maximum reuse.** This is structurally identical to `personal-assistant` (ADR 0005): a single draft-only Agent whose entire behavior lives in its system prompt, using the existing `read-file`, `inkbox-save-draft`, and `send-email` Tools exactly as they already exist. It doesn't belong inside `personal-assistant` itself — that Pack's domain is returns/reservations/general admin, not career/application coaching, and PROJECT-BRAIN.md already named this as its own future Pack — but it needed no new Tool, no new Core type, and no new approval-gating logic. `career-advisor` registers into `config/load.ts` next to the others, with a `description` so the Dispatcher (ADR 0008) can route a plain-English goal like "help me prepare my Chrysalis application" to it automatically.

**No profile/application persistence was built.** The system was checked for any existing store of a user's research history, CV, or career facts (none exists) and for any existing cross-Run memory mechanism (none exists — a Run's Session lives and dies with that one conversation). Building either now would be guessing at a shape ahead of a second real need for it, the same reasoning ADR 0005 already applied to Run's "waiting" states before send-email existed to design against. For now, "tracking requirements and the deadline" happens inside each conversation via a fixed `## Requirements Checklist` section the Agent must always produce, based only on what's been said in that conversation (including facts a returning user re-pastes from an earlier draft) — not a new stored record.

**The Chrysalis Project's facts (deadline, eligibility, required components) are hardcoded into the system prompt, sourced directly from what the user stated when asking for this Pack** — this is legitimate context, not fabrication, since Core has no live access to AAAAI's site and none was requested (browser/portal automation for AAAAI is explicitly out of scope here). What the prompt explicitly refuses to hardcode is the literal wording of AAAAI's prompt question to the faculty letter-writer: that specific text was never given, and inventing plausible-sounding institutional wording from general model knowledge is exactly the kind of unverifiable claim this project's medical-safety discipline (Section 7) already guards against elsewhere. The Agent is instructed to ask the user for that exact text (e.g. copied from the actual application portal) rather than guess at it.

**Never drafts the recommendation letter itself.** The Agent drafts the *request message* to the chosen faculty member, and — if the user gives it the portal's actual prompt question — includes that verbatim, but the prompt explicitly forbids producing the letter's content: that must remain the faculty member's own genuine assessment, not agent-generated text laundered through a human signature.

# LinkedIn/Indeed coverage in the scheduled pipeline, via the same mailbox ADR 0013 already built for

ADR 0013 gave `job-search-agent` — the interactive Pack, driven inside an orchestrator Run — a way to read LinkedIn/Indeed listings safely: forwarded job-alert emails, read through Inkbox, never automation against linkedin.com itself. That reasoning stands unchanged here. What ADR 0013 didn't reach is the pipeline this project actually runs unattended: `src/jobsearch/`, built in ADR 0014, has never read mail at all. Its sources were Greenhouse, Lever, Ashby, and generic feeds — LinkedIn and Indeed were coverage the scheduled digest simply didn't have.

**A session's own connectors don't reach the scheduled run, so the fix has to be the same mailbox, not a personal inbox.** Connecting a real Gmail account as a Claude connector lets an interactive chat read it — but `node dist/cli/index.js jobs run`, invoked by launchd on a schedule, has no Claude session and no connector access at all. The only credential surface it has is environment variables. So the only way LinkedIn alerts reach the *unattended* digest is a mailbox reachable by API key — which is exactly what ADR 0013 already established (`toozy@inkboxmail.com`, or whichever Inkbox mailbox is configured) and exactly why connecting her personal email as a connector would not have actually solved the problem being asked, on top of handing over her entire inbox instead of just job alerts.

**No second Inkbox client.** `src/integrations/inkbox/real-client.ts` already exists — a real, tested `InkboxClient` implementation calling Inkbox's documented Mail API directly (ADR 0002's zero-runtime-dependency stance, same as the Anthropic provider). The new source in `src/jobsearch/sources/alert-mail.ts` takes that same `InkboxClient` port rather than building a parallel HTTP client. One set of credentials (`INKBOX_API_KEY`, `INKBOX_MAILBOX_ADDRESS`) serves both the interactive Pack's tools and the scheduled pipeline's source — and since the pipeline only needs to poll `searchMail`/read messages once per scheduled run (not continuously), it needs neither the webhook receiver nor its signing key that real-time inbound delivery would require.

**The honest limit of this ADR: the extraction was never checked against a real LinkedIn alert email.** Greenhouse, Lever, and Ashby are documented JSON APIs, verified live against real boards before a single line of watchlist config was written. A LinkedIn alert email is not a documented format — it's marketing-team HTML that can change without notice. `extractListingsFromEmail` is built from the publicly known general shape (a title link to a job-view URL, followed by "Company · Location" text) and is deliberately conservative: no job-view link, no listing; no identifiable company, no listing; an ambiguous single segment is read as the company rather than guessed into the wrong field, and that specific failure mode is a locked-in test case, not a hidden one. But it has not been proven against a real sample, because none had been forwarded at the time this was built. This is not a "may not work" hedge to be quietly forgotten — the first real batch of alerts through this pipeline should be checked by hand against what this source extracted, the same way every other source in this project earned trust by being run against real data before being relied on unattended.

**What this doesn't change.** Nothing here touches linkedin.com or indeed.com directly, in any form — the boundary ADR 0013 drew stays exactly where it was. The alert-mail source is additive: `sourcesFromWatchlist` and the watchlist's per-company model are untouched, since a shared alert mailbox isn't a per-company source and doesn't fit that shape. When Inkbox isn't configured, `createInkboxClientFromEnv()` returns `undefined` and the pipeline runs exactly as it did before this ADR — the same "never a half-configured client" pattern already used for the scoring client.

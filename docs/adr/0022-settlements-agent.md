# Settlements agent: deadline tracking and eligibility research, with no filing path

The owner tracks a pipeline of class-action settlement claims: deadlines, estimated payouts, eligibility, status and confirmation numbers, plus a list of settlements he has evaluated and dropped. Every claim form requires his own sworn attestation, so **nothing in this project files, attests or submits a claim** — there is no gated path, as there is for Sleeper league writes (ADR 0021). The agent's job is to make sure he never misses a deadline, knows exactly what only he can do, and never wastes time re-researching something he already ruled out.

**One tracker, rules in one place.** `src/settlements/tracker.ts` holds every rule: statuses move only along allowed paths (`researching → ready_to_file → filed → paid`, any open status → `dropped`), and every change needs the owner's evidence text. `ready_to_file` needs an `eligible` verdict with evidence. `filed` needs the day he filed and takes only the confirmation number he supplies; nothing generates one. `dropped` is final and adds the settlement to the permanent do-not-research list. Storage (`storage.ts`) only loads and saves one JSON document, so the in-memory and file-backed versions can't drift apart the way two full store implementations can. The file lives at `.orchestrator/settlements/tracker.json` (gitignored). A tracker file that exists but can't be parsed is an error, never a silent reset — resetting would lose confirmation numbers.

**Provenance on every fact.** A deadline, a payout and a verdict each carry their source. Payout text is quoted as the source states it ("Up to $800", "Varies") and never replaced by a computed figure. When sources disagree on a deadline, the disagreement is recorded, the owner's recorded deadline is not changed, and reminders act on the earliest date. The seed (`seed.ts`) holds the owner's pipeline as of 2026-09-25 with his deadlines, and payouts and class definitions read that day from Top Class Actions, ClassAction.org and the Amazon settlement's official site. ClassAction.org lists the non-bank ATM deadline as 2027-02-27 while the owner and Top Class Actions have 2027-02-10; that conflict is seeded and alerts use 2027-02-10.

**Personal data stays out of the repository.** This repository is public. The CVS confirmation number is not in the seed; the owner records it locally once with `settlements confirmation cvs-digital-privacy <number>`, and review flags it until he does.

**Deadline engine.** `deadlines.ts` is pure: days left in the owner's timezone (America/Chicago by default, `SETTLEMENTS_TIMEZONE` to override), urgency bands, and nudges at 14, 7, 3 and 1 days left. Each nudge is keyed by settlement, deadline and threshold and recorded when delivered, so it never repeats. If several marks were crossed since the last run, only the tightest fires. An extended deadline is a new key, so it gets a fresh set of nudges. Overdue items are never auto-dropped; review says the deadline passed and how to record it.

**Eligibility evaluator.** `eligibility.ts` checks requirements against the owner's profile (Texas resident; CVS app user; received robocalls/texts; iPhone user; Amazon shopper with botched refunds; renter). A requirement is a residence limit, a profile fact, or evidence only the owner holds. Any failed requirement → `not_eligible`; all met → `eligible`; otherwise `unverified`, listing the evidence needed. A profile match never stands in for defendant-specific evidence: getting robocalls doesn't prove USA Clinics texted him. The evaluator's result is shown next to the owner's recorded verdict and never overwrites it.

**Research pipeline.** `research/` reads two public pages with plain GETs: Top Class Actions' open-settlements RSS feed (a fact box per article: eligibility, award, proof, deadline, website) and ClassAction.org's settlements page (a card per settlement). Listings from different sources merge when they share the official settlement domain, or, with no domain on one side, when their distinctive name tokens overlap strongly; generic words like "data breach" never merge two settlements, because a wrong merge hides one. Each result is sorted into do-not-research (skipped), already tracked (deadline differences recorded as conflicts), seen before, expired, or new. New ones are evaluated, ranked by a 0–100 priority (fit, conservatively-read payout, urgency, effort) and saved to a research inbox. Only the owner moves a candidate into the tracker (`settlements add`, which requires a sourced deadline) or rules it out for good (`settlements dismiss`). A failed or redesigned source is reported and the sweep continues. Tests run against trimmed copies of both real pages captured on 2026-09-25.

**Agent and tools.** `settlements-agent` has four tools: deadlines, review, evaluate (all read-only) and research sweep, whose only write is to the research inbox. No tool changes a status, sets a verdict, records a confirmation or adds to the tracker; those are CLI commands the owner runs with his evidence. Tests check that no tool or CLI command can file, attest or submit, that running every tool leaves statuses, verdicts and confirmations unchanged, and that the settlements source code has no non-GET request or browser automation.

**Changes from the Sleeper pattern.** The CLI declares each command's usage once, and the help text and every usage error come from that declaration, so they can't drift. `loadDefaultConfig` takes new dependencies through a named options bag rather than an eighth positional parameter. The clock is injected rather than read from the environment inside Tools.

Not built: automatic delivery of nudges (running `settlements alerts` is manual, per the "unattended execution" boundary in PROJECT-BRAIN), sources beyond the two above, reading the owner's mailbox for breach notices, and anything that touches a claim form.

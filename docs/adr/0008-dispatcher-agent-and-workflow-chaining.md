# A Dispatcher agent and real workflow chaining across multiple Agents

PROJECT-BRAIN.md's Section 11 has always listed "a full multi-step workflow engine (chaining multiple agents/tasks together automatically)" as explicitly not being built — deferred, per this project's own stated philosophy, until a real need justifies it rather than guessed at ahead of time. That need now exists: the goal is to state an idea in plain English once and have the system figure out which Agent(s) should handle it and actually run them, rather than the user picking an Agent and running it by hand every time.

**A `Workflow` (`src/core/workflow.ts`) is a new Core type, not a bigger Run.** It's an ordered sequence of `WorkflowStep`s, each naming one Agent and its own instructions; each step, once executed, is a completely ordinary `Run` in the existing `RunStore` — a Workflow doesn't replace or duplicate Run/Result, it just records how several real Runs chain together. This keeps every existing single-Run capability (approval gating, waiting-for-response, audit history) exactly as-is; a Workflow inherits them by construction rather than reimplementing them.

**Planning is itself an ordinary Run, not a special code path.** A new `dispatcher` Agent (`src/packs/dispatcher/`) has no Tools — its only job is to read a goal plus a plain-text list of available Agents (name + one-line `description`, a new optional field on `AgentDefinition`) and reply with a fenced ` ```json ` block naming an ordered plan. `workflow-runner.ts`'s `planWorkflow` runs this through the exact same `runToCompletion` every other Agent uses, then parses the reply. An Agent needs a `description` to be dispatchable at all — `default`, `demo`, and the Inkbox-specific utility agent are deliberately excluded (see `dispatchableAgents` in `config/load.ts`), since routing to them was never their job.

**Execution reuses `advance`/`runToCompletion`/`approveAndExecute`/`resumeWithReply` verbatim — Core Workflow logic is only a sequencing layer on top.** `runWorkflowToCompletion` runs each step's Task (with the previous step's output appended as context) until the whole chain succeeds, or the first step that pauses or fails stops it — a paused step never lets a later step start. `AgentResolver` is a caller-supplied function (`(agentName) => {agent, deps}`), not a Registry lookup Core performs itself — Core still never depends on Registry or does I/O; the CLI resolves real Providers/Tools and decides when to persist each step's Run (`WorkflowRunHooks.onRunUpdate`).

**A known, deliberate simplification: approving a workflow step's gated action always lands on `waiting_for_response`,** because that's what `approveAndExecute` already does — a Workflow's `awaiting_approval`/`waiting_for_response` states are a direct mirror of `RunStatus`, not a new state machine. This matches ADR 0005's send-email-shaped assumption; a future gated Tool that doesn't conceptually "wait for a reply" would need Core changes at that point, not before.

**CLI-level approval stays a real human checkpoint, but generalized.** `send-email`'s existing `approve-send` command requires retyping every field by hand as the approval input (ADR 0004's exact-match design). A Workflow can pause on *any* gated Tool from any Agent, so `orchestrator dispatch approve <id>` instead prints the exact pending input and requires a separate `--yes` flag to confirm it verbatim — still a real, deliberate human step (nothing executes on the first call), just one that works generically across whatever Tool happens to be pending, instead of a Tool-specific set of CLI flags.

**Not built by this ADR:** anything resembling ongoing project monitoring, unattended background execution, or an agent that reports on multiple external projects unprompted. Today's Dispatcher only runs when explicitly invoked via `orchestrator dispatch run`, exactly like every other Agent in this project — the persisted `Workflow`/`Run` history this ADR adds is what a future "status across everything" capability would read from, but building that reporting layer is a separate, later decision, not implied by this one.

# Texting the daily digest, as its own gated capability

Every other output of `src/jobsearch/` is passive: a file on disk, a page served on `localhost`. Texting the digest is the first thing in this pipeline that reaches out and touches a real device, unattended, on a schedule — a different category of action from anything ADR 0014 or ADR 0015 built, and it gets its own boundary rather than being folded into either.

**Three independent gates, not one.** `sendDigestSmsIfConfigured` (in `jobs-commands.ts`) only sends when `INKBOX_API_KEY`/`INKBOX_SMS_PHONE_NUMBER_ID` resolve to a real client, `DIGEST_SMS_TO` names a destination, *and* `DIGEST_SMS_ENABLED` is the literal string `"true"`. The third gate is the one that matters most: having credentials configured — to build against, to test the plumbing, to confirm `jobs sources` reports things healthy — must never be the same condition as live automated texts going out to a real phone. Every other credential in this project (the Anthropic key, Inkbox's mail credentials) is "configured or not"; this one additionally asks "and do you mean it," on purpose.

**Real prerequisites this code cannot satisfy, and does not try to.** Inkbox's own Phone API requires the destination to be recorded as opted in via `smsOptIns.optIn()`, which itself requires the account to be on an active, carrier-registered 10DLC campaign — real-world SMS compliance infrastructure, not a config value this pipeline could set for itself even if it wanted to. Nothing in this codebase calls `optIn` on anyone's behalf; that stays a deliberate, one-time action taken through Inkbox directly, by a human, before this is ever switched on. A send that fails because the recipient isn't opted in yet surfaces as `SmsRecipientBlockedError`, reported plainly, and never fails the run — the digest itself was already written to disk before this step runs at all.

**A new, small, separately-testable client, following the shape `ScoringClient` (ADR 0014) already established for this project's "own port, not the orchestrator's abstraction" pattern.** `SmsClient` in `src/jobsearch/sms-client.ts` is a two-method interface with a real fetch-based implementation and a fake for tests — same reasoning as before: the orchestrator's `ModelProvider`/`Tool` machinery is built for an interactive agent Run with an approval queue, and a scheduled script sending exactly one message per run doesn't fit that shape any better than batch scoring did.

**The request shape is copied from the installed `@inkbox/sdk` (v0.6.6), not guessed** — `POST /numbers/{phoneNumberId}/texts`, header `X-API-Key`, base `https://inkbox.ai/api/v1/phone` — read directly out of `node_modules/@inkbox/sdk/dist/phone/resources/texts.js` and `dist/inkbox.js`, the same discipline `real-client.ts`'s own header comment describes for the Mail API. One discrepancy surfaced by actually reading the installed SDK rather than assuming: the currently-installed SDK sends `X-API-Key` for every resource, Mail included, while this project's existing Mail client sends `X-Service-Token`. That's worth knowing and worth someone checking against a real mailbox — but it's `real-client.ts`'s own tested behavior, unrelated to the code this ADR adds, and not something changed here without evidence either header is actually wrong in practice.

**Content, per Shivani's own stated preference over the dashboard-link-only default this project first proposed:** every role gets its own apply link in the text itself, not one link back to the dashboard — `formatDigestSms` in `src/jobsearch/digest-sms.ts` lists up to `DIGEST_SMS_MAX_ROLES` (default 5) roles with title, company, score, a stated salary when there is one, and its direct link, then names how many more are waiting on the dashboard rather than silently truncating.

**No dependency on ADR 0015's alert-mail source, or vice versa.** Both reuse Inkbox, but through different resources (Mail vs. Phone) with different credentials, and either can be configured without the other.

# Gated form-filling: a deliberate reversal of ADR 0007's read-only boundary

ADR 0007 built the browser Tool with no click/type/submit method anywhere in the port, as a structural guarantee, not a policy one — the explicit statement there was that adding write actions "should get the same ADR 0004 treatment... this ADR is explicitly not that." This ADR is that: a real need arrived (initiating a retailer return/refund without the user manually filling out the form themselves) and the user explicitly chose to build real write capability rather than the safer "prepare and stage only" option, after being told the tradeoff plainly (a live, hard-to-reverse action on a third-party site; most platforms' own terms restrict automated interaction with their own support flows).

**The safe/consequential split is identical to `inkbox-save-draft`/`send-email` (ADR 0004), applied to a new domain.** A new port, `FormFillingClient` (`src/integrations/browser/form-client.ts`), has three operations:
- `listFormFields` — read-only, shows the real fields a form has (selector, label, type) so an agent never guesses at a field name.
- `previewFormFill` — safe. Fills values into the page and reports back exactly what would be submitted, but never clicks anything. Filling a form that's never submitted has no more external effect than saving an email draft.
- `submitForm` — consequential. The only operation anywhere in this port that clicks a submit control on a real page. Its Tool (`browser-submit-form`) is the only one of the three marked `requiresApproval: true` — the Orchestrator's existing exact-match approval gate (ADR 0004) is what actually prevents it from running unattended; the port itself has no gate of its own, the same way `InkboxClient.send()` relies on the Orchestrator rather than gating itself.

**Not bound to one site at construction, unlike `BrowserClient` (ADR 0007).** Reading Sermo's feed only ever needed one authenticated session, so `BrowserClient` is constructed once per site. Form-filling needs to work against whichever retailer's site the user is dealing with that day, so `site` is an optional parameter on every call instead — `browser login <site> <url>` still works exactly the same way to authenticate one site's session first, but a public return-request form that needs no login can be used with no site at all. One registered Tool instance now works against any site, rather than requiring new code (and a new Pack/Tool registration) for every new retailer.

**Real-world reliability caveat, stated plainly rather than glossed over:** form structures vary wildly across sites, some are heavily JavaScript-driven or behind CAPTCHAs Playwright can't solve, and `listFormFields`'s field-detection (by `id`, `name`, associated `<label for>`, or `aria-label`/`placeholder` as a fallback) is a best-effort heuristic, not a guarantee it finds every field correctly on every site. The first real attempt against any given retailer should be expected to need iteration, not assumed to work end-to-end on the first try.

**Explicitly flagged, not built here: pointing this at Facebook Marketplace specifically.** The user raised wanting an agent that manages buying/selling on Facebook Marketplace. Facebook's terms of service are unusually aggressively enforced against automated interaction with their platform, and the realistic risk is the user's own account being suspended, not just a technical hurdle — this is a materially different risk category from a retailer's own return form, and deliberately not something this ADR builds a case for. The generic capability built here *could* technically be pointed at any site once a session exists for it, but doing so against Facebook specifically is a decision this ADR leaves to the user to make deliberately, with that risk understood, not something the system defaults into.

**`personal-admin`'s prompt was updated, not any other Pack.** This is squarely a returns/customer-service capability — the Pack it already lived in conceptually. The prompt gives the model an explicit three-step order (list fields, preview fill, only then propose submit) and an explicit instruction not to assume a new site is safe or appropriate to automate against, since that's a real-world judgment call for the human, not something the model should default to attempting.

# Job Search Pack, session-optional browser reads, and an honest gap in daily automation

The first Pack in this project outside medicine: a job-search and resume-tailoring assistant, built for a concrete request relayed through the user (his wife's actual resume and instructions, retrieved from a passcode-protected Amazon secure-attach link via the same Playwright automation built for Sermo/form-filling earlier the same day). Same shape as `career-advisor`/`case-report-writer`: one draft-only agent, no new Core concepts, and — deliberately — no submission-capable tool of any kind. `job-search-agent` can find and describe listings and draft a tailored resume; it cannot apply to anything, because no such Tool exists for it to call.

**`BrowserClient` (ADR 0007) gained an optional-session mode.** The original design assumed every site needing browser reads is a private, authenticated feed like Sermo — `RealBrowserClient` unconditionally required a saved `browser login` session. A public job board's search-results page needs no login at all, so requiring one would have forced either a pointless login step or a design workaround. `RealBrowserClient` now takes a `requireSession` option (default `true`, preserving Sermo's exact original behavior untouched) and `createPublicBrowserClient(siteName)` always returns a real client with no session requirement — mirroring the option `FormFillingClient` (ADR 0011) already had per-call. A new Tool, `read-job-board-page`, is the read-only counterpart to `read-web-page` for this case.

**Resume tailoring reuses the exact anti-fabrication discipline already established**, extended with an explicit rule specific to this domain: a tailored bullet must trace back to something real in the original resume, and a job's desired skill the resume doesn't support at all gets named as a gap, never invented into existence. The user's own instruction (passed through by his wife) explicitly demanded this, which happens to be exactly this project's own standing principle.

**What this ADR does NOT solve: truly unattended daily delivery.** The request was for jobs to be "surfaced every day" — but this system has no scheduled/unattended execution today (a real gap the roadmap already named), and building one exposes a second, sharper problem: `send-email` is unconditionally `requiresApproval: true` (ADR 0004) with no exception, so a scheduled run has no human present to approve a delivery email — it would simply stall in `awaiting_approval` forever. Nothing in this ADR weakens that gate to work around it. The only channels this project's own code can reach without a human in the loop are local files (`RunStore`) — genuinely ambient delivery to an inbox or a shared document would need either a new, directly-integrated delivery channel (e.g. a Drive API adapter with its own credentials, built into this codebase rather than borrowed from the operator's own session tools) or a deliberate, scoped exception to the send-email approval gate for this one non-consequential, informational case — both are real architecture decisions this ADR leaves open rather than defaults into. Running `job-search-agent` today means invoking it explicitly (`orchestrator run --agent job-search-agent` or `orchestrator dispatch run`); a recurring launchd schedule can trigger that same invocation, but the result lands in `RunStore`, not in anyone's inbox, until that decision is made.
